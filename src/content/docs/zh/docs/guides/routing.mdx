在左侧 **Inference → Routes** 打开路由页。2.0 使用三层拓扑：客户端请求先按模型、路由组、协议与 operation 命中 **Request Surface**；Surface 指向一个 **Route Pool**；Pool 内包含多个具体的 **Upstream Target**。这样 Chat、Images、Audio 等操作可以使用独立故障转移池和路由策略。

列表支持多条件筛选；筛选结果会反映在浏览器地址栏，便于复制链接给同事查看同一视图。

</Aside>

## 在管理台里要做什么

<Steps>
1. 打开 **Routes**。
1. **Request Surface**：选择客户端模型与 `route_group`（常用 `default`），再指定入口协议 / operation，例如 `openai.chat`、`anthropic.messages`、`openai.images.generations`；Gemini 流式与非流式统一选择 `gemini.models.generate`。
1. **Route Pool**：让 Surface 指向一个故障转移池；可设置 Pool 默认策略，也可点击各 priority 层的策略 chip 单独覆盖该层。未设置时继续继承模型 / 全局策略。
1. **Upstream Target**：选择 Provider、填写上游实际模型名与 operation，设置 **priority**（数字越大越先试）、**weight** 和启用状态。
1. **计费**：在 Target 的 Billing 配置 **用户计费 / 供应成本** 相对目录标准价的基础倍率；如需对齐供应商高峰 / 闲时价，再配置 **Daily schedule**（每日时段倍率，时区见 [系统配置](/zh/docs/guides/system-config/)）。
1. **保存后**：用 [Playground](/zh/docs/features/playground/) 针对单条路由做上游试跑；若要验证「真实密钥 + 网关入口」整条链路，请用 [Simulator](/zh/docs/features/simulator/)。
</Steps>

## 与客户端的关系

客户端只需传 **`model`** 及协议要求的请求体，无需写死供应商信息。可使用基础模型 ID，或用 `baseId:group` 选择路由组。

## 路由顺序与四种策略

Pool 先按 Target 的 `priority` **降序分层**，数字越大越先试；同一 priority 层再按生效策略与 `weight` 排序：

| 策略 | 特点与适用场景 |
|------|----------------|
| `cache_affinity`（默认） | 同用户、模型、分组与协议稳定首选同一 Provider，Prompt Cache 命中率高；短时流量可能不完全均匀。 |
| `weighted_random` | 按 weight 加权随机分流，负载均衡性高，适合比例分摊或 A/B；缓存亲和较弱。 |
| `fixed_order` | 同层按 weight 从高到低固定排序，适合可预测主备；首选 Provider 承担大部分流量。 |
| `weighted_round_robin` | 按 weight 轮转，更均匀；计数器按运行实例维护，多实例间不全局同步。 |

跨供应商硬主备请使用不同 `priority`。策略覆盖顺序为：当前 `priority` 层覆盖 → Route Pool 默认 → 模型 capability 规则 → 模型 protocol 规则 → 模型默认 → 全局 `ROUTE_STRATEGY` → `cache_affinity`。

## 故障转移与熔断

可重试的 429、401 / 403、5xx 与网络错误会继续尝试下一个 Target；Provider 会按错误类型进入不同冷却时间。若所有候选都处于熔断状态，Proxy 返回 429 并携带 `Retry-After`。

## 说明

**Playground** 直连单条 Target，不经过 Pool 策略、故障转移、用户计费或请求日志；完整行为请用真实 Proxy 调用或 **Simulator** 验证。图片生成路由须为 OpenAI 协议，见 [图片生成 / 编辑](/zh/docs/guides/images/)。
