一条调用先匹配客户端的**请求入口（Request Surface）**，进入**路由池（Route Pool）**，再尝试其中的**上游目标（Upstream Target）**。模型 ID、路由组、协议和操作共同决定入口。

## 建立第一条路由

1. 准备好供应商和模型，选择匹配的协议适配器。
2. 检查客户端协议与操作，例如 Chat、Responses、Messages、图片、音频或向量。
3. 选择路由池与分组，填写上游模型名、供应商、优先级和权重，启用并保存。
4. 用调试台测试上游，再用模拟器验证入口到记账的完整链路。

图片客户端使用 OpenAI 接口时，上游也可以是已实现转换的原生协议；不是所有操作都可任意转换，见[能力边界](/zh/docs/capabilities/)。

## 优先级与四种策略

`priority` 越大越先尝试。同一层由生效策略决定顺序：

| 策略 | 适用方式 |
|---|---|
| `hash_affinity`（默认） | 稳定首选，保持同用户、模型、分组与协议的缓存连续性 |
| `weighted_random` | 按权重随机分流 |
| `weight_priority` | 同层按权重从高到低固定主备 |
| `weighted_round_robin` | 按权重轮转；运行实例间不共享计数器 |

支持按优先级层覆盖策略。没有有效覆盖时逐层继承路由池、模型和全局规则，准确优先级见 [路由策略参考](https://github.com/OctaFuse/octafuse-gateway/blob/v2.19.0/docs/developers/reference/route-strategies.md)。

## 供应商粘性

粘性记住上次成功的上游目标，并在有效期内优先复用；它与层内策略独立，默认关闭。点击「Provider 粘性」可配置有效期、查看绑定分布与用户明细、逐条解绑或清除整个池的绑定。

![供应商粘性绑定明细与解绑](/screenshots/v2-18-0-sticky-bindings.webp)

解绑后会重新选路，仍可能选回原目标。绑定跨实例共享，`hash_affinity` 则是无状态哈希，两者用途不同。

## 自定义请求头与请求体

请求头和 JSON 请求体分别配置，默认客户端显式值优先。两侧各有独立的强制覆盖（Force override）开关：启用哪一侧，哪一侧使用路由值优先。不要把需要发送给上游的请求头误写入 JSON。

![路由请求头、请求体和强制覆盖](/screenshots/v2-10-0-route-force-override.webp)

## 价格与有效期

供应商倍率、用户计费倍率和供应成本倍率分别维护；供应商倍率还可限定有效期。模型官方时段和路由分时窗口各有职责，保存前查看完整价格预览。用户倍率的合成方式见[额度、价格与折扣](/zh/docs/guides/billing/)。

## 失败后会发生什么

可重试的供应商故障会触发后续候选尝试；熔断避免反复请求不可用账号。流式首事件判断不把注释心跳当成有效内容；首事件超时默认 60 秒，仍有可用候选时可换路，最后候选由首包超时兜底。

用[请求流程与时间线](/zh/docs/guides/request-logs/)查看实际尝试，不要只凭最终供应商猜测路由过程。详细错误、超时与重试条件见 [请求生命周期](https://github.com/OctaFuse/octafuse-gateway/blob/v2.19.0/docs/developers/architecture/proxy-request-lifecycle.md)。
