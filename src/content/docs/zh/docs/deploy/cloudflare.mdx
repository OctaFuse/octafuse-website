Cloudflare 形态下，Proxy 和 Admin 分别运行在 Worker，共享同一 D1。它是一种受支持的部署选择；资源限制和运行费用取决于所选平台套餐与实际用量。

## 使用引导脚本

准备 Cloudflare 账号、Node.js 与 npm，在目标 Gateway 版本的仓库中运行：

```bash
npm install
npx wrangler login
npm run bootstrap:cloudflare
```

按脚本提示创建或选择资源、设置管理后台密码，并记录输出的 Proxy 与 Admin 地址。完整的资源、变量和故障处理以 [Cloudflare 快速部署参考](https://github.com/OctaFuse/octafuse-gateway/blob/v2.19.0/docs/operators/deployment/cloudflare-quickstart.md) 为准。

## 部署后配置

1. 登录 Admin，配置供应商、模型与路由，创建测试用户和用户密钥。
2. 先验证普通请求，再验证业务使用的图片、音频、向量或 MCP 操作。
3. 使用实时能力时，检查对应原生 WebSocket 连接和回传事件。
4. 查看请求流程与账户变化，避免只根据 `/health` 判断业务可用。

## 更新版本与迁移

固定目标版本，先阅读[升级与迁移](/zh/docs/deploy/upgrades/)。备份 D1，执行该目标版本尚未应用的迁移，再更新匹配版本的 Proxy 和 Admin。已有 Workers Builds 或其他 Git 集成部署按各自配置执行，不要额外重复发布一套资源。

密钥放入平台 Secret 或部署配置，生产资源标识不要写入公开文档。需要改用 Postgres 或 MySQL 时，先阅读[部署模式](/zh/docs/deploy/overview/)与数据库切换参考。

运维配置与构建路径见 [Cloudflare 运维参考](https://github.com/OctaFuse/octafuse-gateway/blob/v2.19.0/docs/operators/deployment/cloudflare.md)。
