OAuth lets users approve MCP access in a client without pasting a user API key. **First integrate an authorization server** that handles login, consent and refresh, and issues or rotates gateway tokens through the Admin API.

## Prerequisites

OctaFuse Gateway is a resource server, not an authorization server. Entering an ordinary login-page URL does not complete the integration. The business identity must also map to a gateway user for charging.

Existing API-key access remains usable. This OAuth flow does not authorize general model APIs or automatically relay an upstream server's OAuth flow.

## Enable discovery

1. Open the Client access & authorization section on the MCP Servers page and find the OAuth 2.0 sign-in (optional) card.
2. Enable OAuth 2.0 sign-in, enter the authorization server's HTTPS origin and save. HTTP localhost is allowed for local development.
3. Switch the connection guide to OAuth and follow the client-specific steps.
4. Authorize and call a tool, then verify the application name and gateway user in logs.

## Tokens, refresh and revocation

- `oat_` access tokens are separate from user API keys and only permit `/mcp` and its subpaths.
- The default lifetime is one hour. Clients may refresh through the authorization server; expiry does not necessarily require signing in again.
- View and revoke tokens by application or user in OAuth access tokens, or inspect grants on user details.
- Disabling the server setting disables OAuth discovery. Revoke issued tokens to prevent their continued use.

## Troubleshooting

Check that the server implements the discovery and token integration before investigating client callbacks and token status. A 401 requires valid authorization; an MCP token is rejected on chat and other endpoints because its scope is limited.

See the [OAuth technical reference](https://github.com/OctaFuse/octafuse-gateway/blob/v2.19.0/docs/developers/architecture/mcp-gateway.md#oauth-授权发现) for discovery, issuance and refresh responsibilities.
